# 幸运抽奖

用户入口 `/lucky-draw`，管理员入口 `/admin/lucky-draw`，侧边栏提供入口，简易模式禁用。独立于原有满员开奖活动。

首次升级后默认关闭。管理员可配置活动开关、每次充值门槛、连续抽奖保底次数和 2–12 项奖品。默认每充值 ¥5 获得一次机会，最多连续 10 次获得余额奖品。默认奖池为 ¥20（0.05%）、¥5（0.5%）、¥2（2%）、¥1（7%）、¥0.5（20%）和谢谢参与（70.45%）。仅在从未抽奖且保持旧版完整默认配置时，迁移自动改用这套初始配置；已有运营配置和中奖记录保留。

充值起算点固定为 **2026 年 10 月 16 日 00:00（北京时间，UTC 为 2026-10-15 16:00）**，不会随服务重启或日期变化向后移动，管理端不可更改。以 `payment_orders.paid_at` 判断起算边界，且必须 `completed_at` 非空、余额充值履约成功；起算前付款但起算后入账的订单不计入，起算后付款但尚未完成入账的订单暂不计入。历史充值、套餐、管理员加款、兑换码、推广转入和抽奖奖金不产生次数。

按实付金额 `pay_amount` 的数值统计，包含订单实收手续费；充值与奖品均按数值处理，不做汇率或充值倍率换算。抽中 20 就给账户余额加 20。退款处理中保留原金额，成功全额退款后不计入，成功部分退款按 `refund_amount / amount` 的比例折减实付数值。可用次数 = max(0, floor(起算后有效充值 / 门槛) + 人工赠送累计 - 已抽次数)。零头保留，退款减少资格但不返还已用次数或删除已发奖记录。用户接口 `total_recharged` 现在表示活动有效充值，不再读取 `users.total_recharged`。首次产生抽奖记录后充值门槛锁定，防止重新折算已用次数。

翻牌子、转盘、滚轮共用同一服务端概率和结果。普通抽奖按整数权重随机，总权重必须为 10000。奖品金额 0 代表未中奖，至少一个正金额奖品。保底次数为 N 时，累计连续 N−1 次未中奖后，下一次只在正金额奖品中按相对权重选择，任何中奖都重置计数。N=1 表示每次必中，N=0 关闭保底。转盘扇区大小用于展示，不表示中奖概率。

活动开关、奖池和保底更新对新的抽奖立即生效，已经发放的奖品保留原值。已完成请求的重试总是返回原记录，即使活动已暂停或规则已更改。暂停不删除次数和历史记录。保底未中奖计数在暂停和规则更新后保留。

后端事务锁定配置及用户余额，检查次数、密码学随机抽奖、保存奖品和规则快照、扣次数、记录保底并发放余额。任一失败整体回滚。同一用户和请求 UUID 唯一；客户端提交当前配置版本，旧版本的新请求拒绝且不消耗次数。客户端会按用户保存待确认请求，超时或刷新后用原 UUID 确认结果。发奖事务同时写入鉴权缓存失效 outbox，提交后失效余额和鉴权缓存。

迁移 `248_lucky_draw.sql` 创建独立配置、用户进度和抽奖记录表；`249_lucky_draw_recharge_start.sql` 固定起算时间、补充充值索引及新版初始奖池，启动时自动执行。使用明细清理不影响活动数据。

接口均需要认证，管理接口还需要管理员身份：

- `GET /api/v1/lucky-draw`：当前用户次数、保底进度、奖池及最近 20 次记录。
- `POST /api/v1/lucky-draw/draw`：`{"request_id":"UUID", "config_version":2,"count":10}`（省略 count 或为 1 时返回原单抽响应，5／10 时返回 records 与 total_awarded），身份取自会话；受现有面板限流控制。
- `GET /api/v1/admin/lucky-draw`：配置。
- `PUT /api/v1/admin/lucky-draw/config`：完整配置及当前 `version`，成功后版本递增；并发编辑旧版本拒绝，刷新后重新保存。

管理页中的「用户次数与抽奖统计」独立区块显示全站有效充值、获得次数、已用次数、剩余次数、中奖次数及累计发奖，按邮箱或完整用户 ID 搜索用户并分页展示相同维度；另按奖品名称及金额统计实际抽中次数和发放总额。顶部总览不随搜索过滤。统计使用独立抽奖记录，不依赖使用明细。

结果展示分级：0 为谢谢参与，0.5／1 为普通，2 为稀有（蓝色），5 为史诗（紫色），20 及以上为传说（金色）；稀有及以上有粒子动画和揭晓效果，尊重减少动态效果的系统偏好。分级只控制视觉，不改变后端概率。页面展示最高奖、每次充值门槛及保底剩余次数。

默认奖池普通期望奖励为 0.245／抽。普通未中奖概率 q=0.7045，10 次保底、从 0 未中奖计数开始的一轮十连，期望奖励为 2.4749700018；十连对应充值 50，面值占比约 4.95%。持续抽奖时保底进度跨批次保留，长期每十抽平均 = 10 × 0.245 / (1 - 0.7045^10) ≈ 2.5260775745，长期面值占比约 5.0522%。后台以十连为单位动态计算「充值额、从零保底开始期望、长期期望、长期占比」，不是保证每轮固定获得该金额。保底时会在正金额奖品中按相对权重选择，每次中奖均重置计数；默认 10 连至少获得 0.5（不承诺固定稀有度）。这是赠送余额面值，不是实际利润或上游成本，尚未计入支付手续费、余额消耗与上游费用。

支持 1／5／10 连抽，后端以同一事务依次抽取、逐次推进保底、扣减总次数并汇总入账。次数不足整批拒绝；并发重复请求返回同一批记录，已提交请求的批次数量不可改变，失败整批回滚。迁移 `250_lucky_draw_batches.sql` 保存批次幂等结果，保留旧单抽请求的结果恢复能力。结果弹窗显示最高单项稀有度、合计奖励和每一抽结果，支持关闭、再次抽取和键盘操作。暖金色抽奖区支持跳过动画和本地演示模式；演示模式不调用抽奖接口、不发奖、不改变次数和保底，也不写入记录，显示内容明确标为模拟。

管理区支持按用户 ID 手动赠送 1–10000 次，备注最多 500 字。迁移 `251_lucky_draw_manual_chances.sql` 保存人工次数与赠送流水，记录操作管理员、目标用户、次数和备注；相同请求重试不重复赠送。暂停期间可赠送，禁用用户拒绝赠送。用户和管理统计均显示人工赠送；可用次数 = max(0, floor(有效充值/门槛) + 人工赠送累计 - 已抽次数)。赠送不修改充值或余额。最近 20 笔人工赠送流水单独展示。前端保存待确认赠送请求，超时后锁定原内容重试。

新增管理接口 `GET /api/v1/admin/lucky-draw/stats?search=&page=1`，管理员认证和审计沿用现有路由。每页固定 20 人。`POST /api/v1/admin/lucky-draw/grants` 接收 `user_id`、`request_id`、`count` 和 `note`；管理员身份从会话获取，操作进入现有管理审计。起算时间由服务端返回；配置保存不会接受客户端对起算点的修改。
